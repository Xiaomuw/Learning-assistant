# 多 Agent 学习助手项目需求文档

> 版本：v0.1  
> 更新日期：2026-04-12  
> 适用范围：`learning-assistant` 当前代码实现与后续迭代

> **历史参考说明**：这份文档记录早期产品需求，里面的 MySQL、Chroma、无正式鉴权、`default_user` 等描述已不是当前实现事实。当前事实请以 [项目当前状态](project-current-status.md)、[AI 交接卡](ai-handoff.md) 和实际代码为准。

## 1. 项目概述

本项目是一个面向学习场景的多 Agent 智能辅导系统，目标是为学生提供“学科知识管理 + 智能问答讲解 + 练习生成 + 学习画像追踪”的一体化体验。

系统当前采用 H5 移动端优先界面，前端负责承载学习流程与交互，后端负责知识检索、讲解生成、题目生成、学习记忆沉淀与模型调度。知识库既支持用户上传 PDF，也支持 URL 抓取与学科知识框架自动生成。

## 2. 建设目标

### 2.1 业务目标

1. 为不同学科建立独立知识库，避免知识串扰。
2. 支持用户按学科上传资料并快速开始学习。
3. 根据问题类型自动选择“讲解 / 检索 / 刷题 / 复习”路径。
4. 为用户沉淀学习记忆，形成弱项、近期主题、练习结果等画像。
5. 提供可切换的大模型能力，支持 GPT、Gemini、Qwen、Llama、GLM、Kimi、DeepSeek 等非 Claude 模型族。
6. 支持 Docker 化部署，并优先使用 MySQL 作为结构化数据存储。

### 2.2 产品目标

1. 保持 H5 页面在手机与桌面端均可用。
2. 让“提问 - 理解 - 练习 - 回顾”形成闭环。
3. 降低用户从零开始建立知识库的门槛。
4. 提供可感知的学习反馈，包括最近学习、薄弱点、练习建议等。

## 3. 用户角色与典型场景

### 3.1 核心角色

- 学生用户：围绕某一学科进行问答、刷题、资料上传和复习。
- 运营/教师用户：创建学科、初始化知识库、配置模型与部署环境。

### 3.2 典型使用场景

1. 用户选择“计算机网络”学科，上传 PDF 讲义，随后提问“TCP 和 HTTP 的关系”。
2. 用户没有现成资料，直接为“高等数学”自动生成学科知识框架后开始学习。
3. 用户输入“给我出两道 HTTP 练习题”，系统直接走练习路径并生成题目。
4. 用户进入学习中心查看最近主题、易错点和建议复习内容。
5. 管理者在后台切换当前聊天模型，以适配账号可用模型与成本要求。

## 4. 产品范围

### 4.1 本期范围

- H5 前端页面：聊天页、刷题页、学习中心。
- 学科管理：创建、列表、详情、删除。
- 知识入库：PDF 上传、URL 抓取、自动生成知识框架。
- 多 Agent 学习流程：路由、检索、讲解、刷题、学习记忆。
- 会话持久化：聊天历史、最新题包、学习画像。
- 模型配置：查询可选模型、切换当前聊天模型。
- Docker 部署：前端、后端、Chroma、MySQL。

### 4.2 暂未纳入本期的能力

- 用户鉴权与多租户权限体系。
- 细粒度后台管理台。
- 文件批量管理、文档版本控制。
- 完整的监控告警、审计日志、用量统计。
- Claude 模型支持。

## 5. 功能需求

### 5.1 学科管理

系统应支持预置学科与新增学科两类来源，并满足以下要求：

1. 用户可查看全部学科列表，列表中需展示图标、描述、文档数量。
2. 用户可创建新学科，系统自动生成合法的学科 ID。
3. 用户可查看单个学科详情及其文档数量。
4. 用户可删除学科，同时删除对应的向量知识库集合。

### 5.2 知识库构建

系统应支持按学科构建独立知识库，并满足以下要求：

1. 支持上传 PDF 文件，解析文本并写入向量库。
2. 支持输入多个网页 URL，抓取正文内容并写入向量库。
3. 当学科暂无资料时，可由 LLM 自动生成基础知识框架并入库。
4. 每个学科应映射到独立的 Chroma Collection。

### 5.3 智能问答

系统应支持围绕当前学科开展学习问答，并满足以下要求：

1. 用户可输入自然语言问题并触发学习工作流。
2. 系统应识别问题类型，包括概念理解、问题求解、复习、刷题等。
3. 对于概念/问题类问题，系统应优先检索学科知识库后再生成讲解。
4. 对于复习类问题，系统应同时生成讲解与练习题。
5. 对于刷题类问题，系统应优先生成题目并更新记忆。
6. 系统应支持 SSE 流式返回中间节点结果。
7. 系统应支持同步接口，便于前端调试和联调。

### 5.4 练习与巩固

系统应支持基于当前问题或最近学习内容生成练习题，并满足以下要求：

1. 题目应包含难度、题干、提示、答案、知识点。
2. 最近一次题包应可在刷题页中恢复展示。
3. 练习结果应与用户学习记忆形成关联。

### 5.5 学习记忆与学习中心

系统应支持沉淀用户学习画像，并满足以下要求：

1. 系统记录最近学习主题。
2. 系统记录薄弱点和错误次数。
3. 系统记录最近一次会话标识。
4. 学习中心应基于后端真实数据展示学习概况。

### 5.6 聊天历史

系统应支持聊天记录持久化，并满足以下要求：

1. 每次问答完成后写入会话记录。
2. 每个会话需保存标题、消息列表、最新题包、更新时间。
3. 前端可读取指定用户的全部历史会话。
4. 用户可删除某条历史会话。

### 5.7 模型切换

系统应提供后台模型切换能力，并满足以下要求：

1. 后端应返回当前聊天模型、Embedding 模型、可选模型列表。
2. 可选模型来源于实时拉取的账号模型列表，并过滤掉 Claude。
3. 切换前应校验模型是否当前账号可用。
4. 当前模型选择应持久化存储。
5. 前端聊天页应展示当前模型并允许切换。

### 5.8 H5 页面能力

H5 前端应满足以下要求：

1. 页面以移动端优先设计为主，同时兼容桌面浏览器。
2. 聊天页应保留学科切换、资料上传、模型切换、问答结果展示等能力。
3. 刷题页应展示最新题包并支持练习流。
4. 学习中心应展示学习画像与近期学习内容。

## 6. 非功能需求

### 6.1 可用性

- 前端需保持 H5 交互友好，适配常见手机尺寸。
- 核心学习链路应控制在用户可感知的响应时间范围内。
- 问答流中需可感知处理阶段，避免长时间无反馈。

### 6.2 可维护性

- 结构化数据统一进入 MySQL。
- 非结构化知识向量统一进入 Chroma。
- 模型访问应抽象为统一 Provider 层，避免散落在业务代码中。
- 文档与接口定义需与当前实现保持同步。

### 6.3 可部署性

- 支持通过 Docker Compose 启动前后端、Chroma 与数据库。
- 环境变量应集中在 `.env` 中配置。
- 前端容器应通过容器内网访问后端 API。

### 6.4 安全性

- 模型密钥、数据库密码必须通过环境变量管理，不得写入代码仓库。
- 当前版本允许开放 CORS 以便开发调试，生产环境需收敛来源域名。
- 当前版本尚未引入用户鉴权，生产使用前需补充认证与权限控制。

### 7.2 已验证

- 模型切换已完成实测

## 8. 约束与已知限制

1. 历史版本曾使用 `default_user`；当前版本已经改为真实账号体系。
2. 可切换模型取决于当前配置的 DeepSeek / OpenAI-compatible provider 账号订阅与开放范围。
3. 模型列表会动态变化，文档中不应将某个模型视为永久可用。
4. 宿主机如果已有进程占用 `3000/8000` 端口，可能影响 Docker 暴露服务的直接访问。
5. 学习画像仍属于轻量结构化沉淀，尚未引入更复杂的掌握度算法。

## 9. 验收标准

### 9.1 功能验收

1. 可创建学科并查看列表。
2. 可向指定学科上传 PDF 并成功入库。
3. 可发起一次聊天问答并得到讲解结果。
4. 可发起一次刷题请求并在刷题页看到题目。
5. 学习中心可读取真实学习记忆。
6. 可查看与删除历史会话。
7. 可查询并切换当前聊天模型。

### 9.2 技术验收

1. 后端服务可正常启动并通过健康检查。
2. MySQL 中已生成核心业务表。
3. Chroma 服务可用且按学科写入向量数据。
4. 前端构建、Lint 通过。
5. Docker Compose 可完成整体部署。
